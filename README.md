# Messenger

Мессенджер на FastAPI, PostgreSQL, HTML, CSS, JavaScript.

## Запуск

### Windows (PowerShell)

Нужны Python 3.10+ и Docker Desktop. PostgreSQL ставится в Docker, ставить
его отдельно не нужно.

```powershell
# 1. Разово: окружение, зависимости, PostgreSQL в контейнере, схема из init.sql
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1

# 2. Запуск: поднимает базу и стартует сервер
powershell -ExecutionPolicy Bypass -File scripts\run.ps1
```

Открыть http://localhost:8000.

Скрипты идемпотентны — `setup.ps1` можно запускать повторно, он доделает
только недостающее и ничего не сломает. Схему он применяет только если в
базе ещё нет таблиц, так что данные не пропадут.

Другой порт: `scripts\run.ps1 -Port 8080`.

Если Docker Desktop не запущен, `run.ps1` скажет об этом и остановится.

### macOS / Linux

```bash
# 1. Зависимости
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt

# 2. PostgreSQL: роль и база (от пользователя postgres)
psql -d postgres -c "CREATE ROLE messenger_user LOGIN PASSWORD 'pass';"
psql -d postgres -c "CREATE DATABASE messenger_db OWNER messenger_user;"

# 3. Схема новой базы. init.sql создаёт её с нуля, migrations/ обновляет существующую
psql "postgresql://messenger_user:pass@localhost:5432/messenger_db" -f init.sql

# 4. Сервер (раздаёт и API, и фронтенд с /)
cd backend && ../.venv/bin/uvicorn main:app --reload
```

Открыть http://localhost:8000.

### PostgreSQL в Docker (любая ОС)

Если PostgreSQL ставить не хочется, базу можно поднять в контейнере.
Реквизиты ниже совпадают с умолчаниями в `backend/database.py`:

```bash
docker run -d --name messenger-pg \
  -e POSTGRES_USER=messenger_user \
  -e POSTGRES_PASSWORD=pass \
  -e POSTGRES_DB=messenger_db \
  -p 5432:5432 \
  postgres:16

# схема из init.sql
docker exec -i messenger-pg psql -U messenger_user -d messenger_db -v ON_ERROR_STOP=1 < init.sql
```

Контейнер останавливается вместе с Docker, данные лежат в нём же:
`docker stop messenger-pg` / `docker start messenger-pg`.

### Доступ с других устройств

По умолчанию uvicorn слушает только localhost, поэтому с телефона сайт не откроется.
Нужен `--host 0.0.0.0`:

```bash
cd backend && ../.venv/bin/uvicorn main:app --host 0.0.0.0 --port 8000
```

`scripts\run.ps1` уже стартует с `--host 0.0.0.0`, так что с телефоном
в той же сети сайт откроется сразу.

Дальше открыть на любом устройстве в той же сети `http://<ip-мака>:8000`.
Свой IP можно узнать командой:

```bash
ipconfig getifaddr en0    # macOS, Wi-Fi
```

```powershell
ipconfig | Select-String "IPv4"    # Windows
```

IP меняется при переподключении к сети, поэтому адрес придётся уточнять.
Файрвол macOS может спросить разрешение на входящие соединения — нужно ответить «Разрешить».
В Windows firewall обычно пропускает Python при первом запуске; если страница
не открывается, разреши входящие соединения для `python.exe` в настройках
«Брандмауэр и защита сети → Параметры входящего подключения».
PostgreSQL при этом продолжает слушать только localhost: браузер ходит напрямую
в FastAPI, к базе он не подключается.

Сессия лежит в `localStorage` и привязана к адресу, поэтому на телефоне
и на ноутбуке это будут два независимых аккаунта — входи под разными никами.

## Мобильная версия

Версия выбирается по ширине окна, порог — 768px (`CONFIG.MOBILE_MAX_WIDTH`),
проверка через `matchMedia` в `Session.isMobile()`.

Мобильная версия состоит из отдельных страниц, поэтому работает кнопка «назад»
в браузере:

- `mobile/chats.html` — список чатов на весь экран;
- `mobile/chat.html?id=N` — переписка на весь экран, `-1` — избранное.

Заголовок чата берётся из `GET /api/chats` по этому `id`, а не передаётся в ссылке,
поэтому кириллица в нике не ломает URL. Если чата с таким `id` нет
(например, ссылка сохранена, а чат удалён), страница возвращает к списку.

Вёрстка рассчитана на телефон: `100dvh` вместо `100vh`, чтобы адресная строка
мобильного браузера не срезала низ, `env(safe-area-inset-*)` под вырез и
«домашнюю полоску» iPhone, у полей ввода `font-size: 16px`, иначе iOS зумит
страницу при фокусе.

### Переменные окружения

`SECRET_KEY`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` — все необязательны,
значения по умолчанию зашиты в `backend/database.py` и `backend/auth.py`.
Для `SECRET_KEY` в продакшене задайте свой, иначе токены можно подделать.

## «Избранное»

Виртуальная папка в стиле Telegram, а не отдельный чат:

- в `chats` и `chat_members` для неё нет ни одной строки;
- сообщения лежат с `chat_id = NULL` и `is_favorite = true`;
- клиент обращается к ней как к чату `-1`, бэкенд переводит это в `chat_id = NULL`;
- папка приватна — видны только сообщения, добавленные самим пользователем.

Обычное сообщение тоже можно перенести в избранное, поставив ему флаг
`POST /api/messages/{id}/favorite`. Флаг ставится только на свои сообщения.
Внутри самого «Избранного» звезда не рисуется: там всё уже в избранном.

## Изображения в сообщениях

Скрепка 📎 рядом с полем ввода открывает выбор файла (`accept="image/*"`),
и выбранная картинка сразу уходит на сервер через `FormData` — отдельной
кнопки «отправить» не нужно.

- `POST /api/messages/upload` принимает `multipart/form-data`: `chat_id`,
  `file`, необязательные `caption` и `reply_to_id`.
- Сервер проверяет, что файл действительно картинка (JPEG, PNG, GIF, WEBP,
  BMP — по сигнатуре, а не по расширению), и что он не больше 5 МБ.
- Имя генерируется через `uuid`, файл кладётся в `uploads/images/`
  (папка в `.gitignore`), а в `messages.media_url` пишется только
  относительный путь `/uploads/images/<uuid>.<ext>`.
- Папка раздаётся как статика: `app.mount("/uploads", StaticFiles(...))`
  в `backend/main.py`.
- Событие по WebSocket содержит `media_url`, клиент рисует `<img>` с
  `max-width: 100%` и скруглёнными углами.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/register` | регистрация по username и паролю |
| POST | `/api/login` | вход по username и паролю, возвращает JWT |
| GET | `/api/users?q=...` | поиск остальных пользователей по username/nickname |
| GET | `/api/contacts` | сохранённые контакты пользователя |
| POST | `/api/contacts` | добавить пользователя в контакты по username |
| GET | `/api/chats` | чаты пользователя, «Избранное» первым |
| POST | `/api/chats` | создать/открыть личный чат по username собеседника |
| GET | `/api/messages/{chat_id}` | история сообщений (`chat_id = -1` — избранное) |
| POST | `/api/messages` | отправить сообщение |
| POST | `/api/messages/upload` | отправить изображение (`multipart/form-data`) |
| POST | `/api/messages/{id}/favorite` | переключить избранное |
| WS | `/ws/{user_id}?token=...` | real-time, рассылает только участникам чата |

Всё, кроме `register` и `login`, требует заголовок `Authorization: Bearer <token>`.

## Аккаунт

У пользователя два разных поля:

- `username` — уникальный логин и адрес для поиска. В базе хранится с ведущим
  `@` (`@ivan`), а в полях ввода — без него. Максимум 30 символов без `@`,
  разрешены латиница, кириллица, цифры и `_`. Регистр учитывается, поэтому
  `Ivan` и `ivan` — разные аккаунты.
- `nickname` — отображаемое имя. Может повторяться у разных людей, максимум
  30 символов, тот же набор символов. При регистрации создаётся автоматически
  из username и потом меняется в профиле отдельно.

Вход выполняется только по username. Если ввести `@`, интерфейс и сервер
попросят писать username без этого символа. При смене username старый сразу
освобождается, nickname остаётся прежним, а сессия продолжает работать:
JWT привязан к `user_id`, а не к username.

В поиске и карточке профиля username показывается рядом с nickname в формате
`nickname (@username)`. В списке чатов и заголовке переписки отображается
nickname собеседника.

## Личные чаты

Кнопка `＋` рядом с выходом открывает поиск по username/nickname и создаёт чат
с выбранным пользователем (`POST /api/chats`, поле `username` — без `@`).
Поиск показывает совпадения без учёта регистра, а при создании чата username
используется точно: `Ivan` и `ivan` — разные адресаты.
Если такой чат уже есть, возвращается он же — второй не создаётся.

В `chats` для этого есть колонка `pair_key` вида `"1:2"` — два id участников по возрастанию.
`UNIQUE` на ней не даёт базе завести два чата между одной парой людей, даже если
запросы придут одновременно. У групповых чатов `pair_key` равен `NULL`,
а несколько `NULL` в `UNIQUE` не конфликтуют.

Список чатов сортируется по времени последнего сообщения, чаты без сообщений — по дате создания.

## Контакты

Экран «Контакты» в левом меню показывает только явно сохранённые записи из
таблицы `contacts`, а не всех пользователей и не участников чатов. Список
сортируется по отображаемому имени с учётом русского алфавита. Нажатие на
контакт открывает существующий личный чат или создаёт новый.

Добавить человека можно кнопкой «Добавить контакт»: поиск идёт по username и
nickname, но в `contacts` сохраняется выбранный пользователь.

В личном чате с человеком, которого нет в контактах, сверху показывается
подсказка с кнопкой «Добавить контакт». После закрытия она больше не появляется
для этого собеседника: закрытые username хранятся в `localStorage` под ключом
`messenger_hidden_contact_suggestions`. Подсказка работает и на десктопе, и в
мобильной версии.

## Удаление аккаунта

Безвозвратное удаление аккаунта реализовано через мягкое удаление (tombstone)
плюс фоновую физическую очистку связанных данных.

### Как это работает

1. Пользователь вызывает `POST /api/account/delete` с паролем и contrôleй фразой
   `УДАЛИТЬ АККАУНТ`.
2. Аккаунт помечается как удалённый: `deleted_at` проставляется, `password_hash`
   стирается, nickname заменяется на `Удалённый пользователь`.
3. Все активные WebSocket-сессии пользователя разрываются.
4. Ставится фоновая задача (`account_deletion_jobs`) на физическую очистку:
   медиа из S3/хранилища, ключи кэша Redis, документы из поискового индекса,
   push-токены и устройства. Воркер обрабатывает джобы через
   `FOR UPDATE SKIP LOCKED`, при падении повторяет попытку с экспоненциальным
   бэкоффом (до 5 попыток, затем `failed` — dead-letter).

### API

| Метод | Путь | Описание |
|---|---|---|
| POST | `/api/account/delete` | Удалить аккаунт (требует пароля и фразы `УДАЛИТЬ АККАУНТ`) |

Пример запроса:

```json
POST /api/account/delete
Authorization: Bearer <jwt>

{
  "password": "supersecret",
  "confirmation_phrase": "УДАЛИТЬ АККАУНТ"
}
```

Ответ:

```json
{
  "status": "deletion_scheduled",
  "user_id": 42,
  "deleted_at": "2026-10-25T15:30:00+00:00"
}
```

### Что происходит с данными

- **Вход**: удалённые пользователи не могут войти — `get_current_user` фильтрует
  `deleted_at IS NOT NULL`, ошибка та же, что при неверном пароле (нет перебора).
- **Список пользователей / контакты**: удалённые не попадают в выдачу.
- **Чат с удалённым собеседником**: остаётся в списке, заголовок —
  `Удалённый пользователь`, сообщения сохраняются (история группы не ломается).
- **Сообщения удалённого пользователя**: остаются в чатах, автор отображается
  как `Удалённый пользователь`. Это отраслевой стандарт (WhatsApp, Telegram,
  Slack) — иначе история остальных участников разрушалась бы.
- **Повторный запрос**: идемпотентен — новая джоба не создаётся, если аккаунт
  уже в состоянии `deleted`.

### Схема БД

Новые колонки в `users`: `deleted_at TIMESTAMPTZ`, `deleted_reason TEXT`.
Новая таблица: `account_deletion_jobs` (outbox для фонового воркера).
Миграция уже в `init.sql`; для существующей базы применить `ALTER TABLE`
вручную (см. `init.sql`, секция «Задачи на физическое удаление данных»).

## Миграции базы

`init.sql` создаёт схему новой базы. Уже работающую базу обновляют файлы из
`migrations/`: `backend/migrate.py` применяет ещё не выполненные файлы по
порядку, все — в одной транзакции. Учёт идёт в таблице `schema_migrations`,
поэтому повторный запуск ничего не делает.

Новая миграция — обычный SQL-файл с номером, например
`migrations/002_add_something.sql`. Его проверяют на копии базы и пушат в
`main`: деплой сам сделает бэкап, применит миграцию и только потом перезапустит
сервис. Вручную на сервере ничего выполнять не нужно. Если миграция упадёт,
она откатится целиком, а старый код и сервис останутся работать.

Локальную базу, созданную раньше, можно обновить вручную:

```bash
cd backend && ../.venv/bin/python migrate.py
```

Миграции пишите совместимыми со старым кодом: сначала добавьте колонку или
таблицу, а удаляйте старое отдельным коммитом, когда новый код уже выкачен.

## Бэкапы и пересоздание базы

Для локальной разработки, когда нужно пересоздать базу по `init.sql`, не потеряв
людей и переписку, есть `scripts/db.sh` — он сам сначала делает бэкап, потом
пересоздаёт базу и возвращает данные поверх свежей схемы. На сервере так делать
не нужно: там схема обновляется миграциями.

```bash
./scripts/db.sh backup            # сохранить текущую базу
./scripts/db.sh list              # посмотреть бэкапы
./scripts/db.sh restore           # вернуть последний бэкап целиком (со схемой)
./scripts/db.sh reset             # бэкап → пересоздать по init.sql → вернуть данные
```

На Windows то же самое делает `scripts/db.ps1`. Он ходит в базу через контейнер,
поэтому `psql` на самой машине не нужен:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\db.ps1 backup
powershell -ExecutionPolicy Bypass -File scripts\db.ps1 list
powershell -ExecutionPolicy Bypass -File scripts\db.ps1 restore
powershell -ExecutionPolicy Bypass -File scripts\db.ps1 reset
```

`reset` — это локальный аналог миграции «с нуля». Бэкапы лежат в `backups/`
(папка в `.gitignore`), каждый сохраняется в двух видах: полный (схема + данные)
и только данные.

Если схема изменилась несовместимо — колонки переименованы или удалены, — данные не лягут.
Тогда база останется пустой и целой, а бэкап целым; причина будет написана в вывод.
В этом случае возвращай полный бэкап (`restore`), он восстановит старую схему вместе с данными.

Создавать и удалять базу может не `messenger_user`, а суперпользователь. Скрипт ходит в `postgres`
через локальный сокет; если это не сработает, задай `ADMIN_URL`:

```bash
ADMIN_URL=postgresql://postgres@localhost:5432/postgres ./scripts/db.sh reset
```

В контейнере `POSTGRES_USER` — суперпользователь, поэтому `db.ps1` ходит в `postgres`
под `messenger_user` и отдельный `ADMIN_URL` ему не нужен.

### Про циклический внешний ключ

`chats.last_message_id` ссылается на `messages`, а `messages.chat_id` — на `chats`.
Из-за этого `pg_dump --data-only` не может залить данные сам, и скрипт на время загрузки
снимает одну сторону цикла, а потом возвращает ограничение и пересчитывает `last_message_id`.

По этой же причине у функции триггера `update_chat_last_message` закреплён
`SET search_path = public, pg_temp`: дамп выставляет пустой `search_path`,
и без этого UPDATE не нашёл бы таблицу `chats`.

## Сообщения в реальном времени

Опрос базы не используется. Сервер держит WebSocket-соединения и сам рассылает новое
сообщение всем участникам чата — `GET /api/chats` клиенту дёргать не приходится.

Отправка при этом идёт обычным `POST /api/messages`: так сообщение попадёт в базу,
даже если сокет по какой-то причине не подключён. Событие о нём уходит после сохранения,
из `routers/messages.py`.

Как это устроено на клиенте (`shared/realtime.js`):

- `Realtime.connect(handler)` открывает `ws://<хост>/ws/<user_id>?token=...`;
- при обрыве соединение поднимается заново с паузой от 1 до 15 секунд, после разлогина — нет;
- своё сообщение не дублируется: `Realtime.markSeen` вызывается в `API.sendMessage`
  по id из ответа, и событие с тем же id отбрасывается;
- список чатов перерисовывается не на каждое событие, а пачкой через `UI.debounce`.

Ограничение: соединения живут в памяти процесса, поэтому запускать uvicorn нужно
в одном воркере (`--workers 1`). С несколькими воркерами клиент, подключённый к одному,
не получит события, отправленные в другой.

## Деплой на сервер

Каждый пуш в `main` автоматически выкатывается на сервер через GitHub Actions
(`.github/workflows/deploy.yml`). Workflow заходит по SSH и в `/root/Messenger`:

1. делает `git fetch` и запоминает новый коммит;
2. сохраняет бэкап базы в `/root/messenger-backups/` (хранятся 10 последних);
3. применяет миграции из нового коммита, ещё не трогая рабочее дерево;
4. делает `git reset --hard`, ставит зависимости из `backend/requirements.txt`
   и перезапускает `messenger.service`.

После перезапуска проверяются `GET /api/health`, главная страница и вход с
заведомо неверным паролем. Последняя проверка должна вернуть `401`, а не `500`:
так деплой замечает, что код обновился, а схема базы — нет.

Разовая настройка — GitHub → Settings → Secrets and variables → Actions:

| Secret | Значение |
|---|---|
| `SSH_HOST` | IP или домен сервера |
| `SSH_USER` | пользователь, под которым идёт деплой (`root`) |
| `SSH_PRIVATE_KEY` | приватный SSH-ключ, публичная часть которого лежит в `~/.ssh/authorized_keys` на сервере |

Повторно выкатить текущий `main`, не создавая коммит: Actions → Deploy to server →
Run workflow. Пуш в другую ветку деплой не запускает — сначала влей изменения в `main`.

Схема новой базы создаётся из `init.sql`. На сервере `init.sql` повторно не
выполняется: изменения существующей базы накатываются только через
`migrations/`, автоматически и в транзакции. Восстановить бэкап можно так:

```bash
systemctl stop messenger
PGPASSWORD=pass pg_restore -h localhost -U messenger_user -d messenger_db \
  --clean --if-exists /root/messenger-backups/messenger-....dump
systemctl start messenger
```

Если менялись зависимости, они доставятся следующим деплоем; venv на сервере
лежит отдельно и git его не перезаписывает.
